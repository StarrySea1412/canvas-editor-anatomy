这篇不打算写成「canvas 教程」——API 速查式的文章太多了。我想做一件更朴素的事：拿一个真实在跑的开源 canvas 富文本编辑器当标本，把一个字从字符串变成屏幕上像素的完整旅程，一层一层拆给你看。每一层都配一个能拨动参数、亲眼看见后果的小样——不是录屏，是确定性模型，参数摊在明面上，你可以自己推翻我的结论。

先立一个判断，全文都靠它撑着：可视化编辑器的难点，从来不是「画」，是「一致」。同一份文档数据，要同时喂给三个互相看不见的消费者——排版引擎要拿它算行宽，绘制引擎要拿它填像素，命中测试要拿它算「鼠标这一下点中了哪个字」。这三个消费者对同一份数据的理解差一个像素，用户就会看到光标和文字对不上、点一下选错字、拖一次选区跳三行。所谓「复杂交互产品」，复杂就复杂在这里。

三个消费者、一份数据、必须完全一致——这就是本文的解剖主轴。剩下的章节，是把这句话拆开验证。

不用 contenteditable 的账本

六个本来自动白送的东西，换成 canvas 之后都要自己付钱——先把这张账单摊开，再逐项去付

先说清楚为什么有人要受这份罪。contenteditable="true" 加一个 div，五秒钟你就有富文本编辑器了：光标、选区、断行、复制粘贴、输入法，全是浏览器白送的。那为什么在线文档、标书系统、报表设计器、电子病历编辑器，一个个都绕开了它？

先说 contenteditable 给出的，和它不给的

它给的是一套对你完全黑箱的排版结果。浏览器把内容和样式渲染成一棵 DOM 树，交给排版引擎，输出一堆高度不可控的盒子。你想知道「第 3 行第 12 个字距离左边多少像素」，唯一的办法是 getClientRects() 遍历——而它的结果依赖浏览器对行内盒子的切分策略，跨浏览器不稳定，性能还差。

这在「写篇文章发出去」的场景里无所谓，但在下面这些场景里是致命的：

  • 分页——A4 纸、页眉页脚、页码、「第几页共几页」。DOM 流式布局天然不知道「页」是什么，你得靠算高度硬切，切点往往落在行中间。
  • 精确复现——用户要求「导出 PDF、打印出来，和屏幕上看到的完全一样」，甚至要求「和 Word 里的版式完全一样」。DOM 渲染依赖字体回退、子像素和浏览器差异，这三样每台机器都不同；canvas 画出来的东西，就是同一份绘制指令，走到哪都一样。
  • 非文本对象——表格跨页拆分、浮动图片环绕文字、表单控件、水印、套打模板的绝对定位。DOM 里每个都要打补丁，补到后面你自己都记不清哪个 hack 在管哪块。
  • 超大文档——几万字加几十个表格的文档，DOM 节点以万计，每次输入触发一次全树样式计算和布局，卡顿是结构性的，不是优化能救的。

于是有了另一条路：自己定义文档模型，自己排版，自己画。文字不进 DOM，进 canvas。这条路换来的是完全的可控和确定——代价是，浏览器本来白送的六件事，你要一件一件自己做，而且每件都要付真金白银的工程时间。

L1文档模型elementList

一个平坦数组，每个字符是一个对象：{ value: '排', size: 16, bold: true }。没有节点树——行和页都是算出来的临时产物，不存进数据。

L2测量measureText

每个字的宽度必须问画布：设好 ctx.font 再 ctx.measureText('排').width。同一个字，换字号就是另一个数。

L3断行computeRowList

从左往右累加宽度，超过 innerWidth 就折。但中文能随便折、英文单词不能拆、标点不能顶行首——三条规矩在这一层打架。

L4成行与定位rowList / positionList

每行记下高度、基线、起始下标；每个字记下四个角的坐标。这份坐标表，后面所有人都在读。

L5绘制fillText

按坐标把字填进 canvas。关键优化：同一字体同一颜色的连续字符合并成一次 fillText——上万次调用变几十次。

L6交互光标 / 命中 / 选区

反向解读 L4 的坐标表：鼠标 (x, y) 落在哪个字的框里？光标画在第几个字后面？选区从哪到哪？

这张图不是教学抽象，是从一个真实项目里量出来的。我解剖的标本是开源项目 canvas-editor（MIT 协议，npm 上叫 @hufe921/canvas-editor），一句自我介绍写得很清楚：「a rich text editor by canvas/svg」。它的绘制核心是一个 2979 行的 Draw.ts，整个 core 目录 117 个 TypeScript 文件、19 个子模块——分工大致就是 FIG. 01 的六层，再加事件、快捷键、右键菜单这些外壳。

一次字符测量的旅行

断行不是数字符个数，是逐字量完再决定往哪折——而这套测量本身，就是整个编辑器最贵的一次往返

先问一个看似幼稚的问题：一个汉字有多宽？十六号字，一个汉字大约十六像素——这个答案对等宽字体成立，对绝大多数中文字体也近似成立。那英文呢？「i」和「W」在同一个字号下，宽度能差三倍以上。所以「这一行能放多少个字」这个问题，诚实的答案是：不知道，得一个一个量。

为什么不能数长度

如果按字符个数切行，一行里塞十个「i」和一串「WWWW」，屏幕上会出现一行很短、一行溢出的惨状。如果按「平均字宽 × 个数」估算，只要出现粗体、字号混排、中英混排、标点，误差立刻累积成可见的错位。真实的排版必须是逐字符的：

断行的最小骨架伪代码 · 与真实实现同构
let x = 0;
for (const el of elementList) {            // 逐个字符元素
  ctx.font = getElementFont(el);             // ① 切字体（斜体/粗体/字号）
  const m = measureText(ctx, el);           // ② 量宽（有缓存）
  if (x + m.width > availableWidth) {        // ③ 超了要折行
    pushRow();                               //    但折点在哪？→ 见下文
    x = 0;
  }
  place(el, x); x += m.width;
}

这段代码在标本项目里对应着 Draw.ts 里 2979 行中的一大段 computeRowList。它比伪代码多出来的每一行，都是一个真实的坑。逐个看。

坑一：measureText 很贵，所以要缓存；缓存的键里必须有字体

ctx.measureText() 是一个同步调用，要穿过 JS 与图形层边界。单次几微秒，但一篇两万字的文档一次完整排版就是两万次；用户每敲一个键、每拖一次选区，都可能触发完整重排。所以所有认真的实现都会加缓存，标本项目里的写法朴素到近乎简陋，却精确地踩在正确性上：

字宽缓存（真实源码，节选）TextParticle.ts
const id = `${element.value}${ctx.font}`;    // ← 键 = 字符 + 完整字体串
const hit = this.cacheMeasureText.get(id);
if (hit) return hit;                        // 命中，零成本
const textMetrics = ctx.measureText(element.value);
this.cacheMeasureText.set(id, textMetrics);
return textMetrics;

「字体串也算进键」是这段代码的灵魂。ctx.font 是一整个字符串——"bold 24px Microsoft YaHei"——粗细、字号、字体名任何一个变了，串就不同，缓存自动失效。如果只拿字符做键，用户把「排」从 16 号改成 24 号，缓存会面不改色地告诉你它还是 16 像素宽，整行排版全部错位。这类 bug 在测试环境里很难发现，因为测试用的都是同一种格式。

顺带一提，测量不用正在显示的那块画布。标本项目在 computeRowList 开头专门造了一块看不见的离屏画布：

离屏测量画布（真实源码，节选）Draw.ts · computeRowList 开头
if (!this._measureCanvas) {
  this._measureCanvas = document.createElement('canvas');
  this._measureCtx   = this._measureCanvas.getContext('2d');
}
const ctx = this._measureCtx!;

原因有二：一是测量只需要 2D 上下文，不需要像素，用可见页的上下文反而要来回切换它的状态；二是可见页的上下文带着 scale(dpr) 变换，在它上面量出来的宽度会被放大 DPR 倍——排版要在 CSS 像素空间做，量宽也得在同一个空间。

另一个更隐蔽的坑：字体没加载完。用 Web Font 时，字体加载前后 measureText 返回不同宽度。如果排版发生在字体到位之前，整篇文档按回退字体排好，字体到位后不重排——用户看到的就是文字「挤在一起」或「稀稀拉拉」。正确做法是 document.fonts.ready 之后再做首次排版。这篇页面自己的小样也遵守这条（你打开页面时小样等了字体才渲染第一次）。

坑二：行高不是「这行最高的字有多高」

几乎所有自研实现都会在这里踩一遍。measureText 返回的 actualBoundingBoxAscent/Descent 是这个字符墨迹的实际上下界——「口」「国」「一」「g」四个字的上下界完全不同。如果按每个字符自己的墨迹算行高，同一行里出现一个「g」（有下沉）或「·」（几乎没有高度），整行就会跳。

标本项目里的解法带了一句注释，比任何教程都说得清楚：

基准字（真实源码，节选）基准字符是一个固定取样的「中」
// 使用基于字体的基准度量以确保一致的行高，避免字符特定度量导致的布局跳动
const basisMetrics = this.textParticle.measureBasisWord(ctx, element.font!);
metrics.boundingBoxAscent  = basisMetrics.actualBoundingBoxAscent  * scale;
metrics.boundingBoxDescent = basisMetrics.actualBoundingBoxDescent * scale;

所谓基准字，就是对每种字体固定量一个「中」字（源码常量 METRICS_BASIS_TEXT = '中'），之后这个字体里所有字符的行高贡献都用它的上下界。同一字体同一字号的行，无论内容是什么，行高永远一致。代价是极端情况下墨迹可能微微探出行盒子——但用户看不见那个，用户只看得见「行高稳不稳定」。

排版里所有「看起来对」的近似，背后都是同一个取舍：牺牲墨迹的绝对精确，换布局的绝对稳定。

坑三：折行点不是「放不下的那个字」

中文的断行可以发生在任意两个字之间（除了避头尾），但英文不行——document 不能折成 docu + ment，否则读者会在行尾看到半个词。所以断行算法遇到英文单词时，要先把它整体量出宽度：整个词放得下当前行剩余空间，就整词计入；整个词比一行还宽，才允许硬拆。标本项目里对应着一段专门的词宽预量：

整词与标点（真实源码，节选）Draw.ts · 折行判定
// 累计行宽 + 当前元素宽度 + 排版宽度(英文单词整体宽度 + 后面标点符号宽度)
let curRowWidth = curRow.width + metrics.width;
if (this.options.wordBreak === WordBreak.BREAK_WORD) {
  const word = `${preElement?.value || ''}${element.value}`;
  if (this.WORD_LIKE_REG.test(word)) {
    const { width, endElement } = this.textParticle.measureWord(ctx, elementList, i);
    const wordWidth = width * scale;
    if (endElement && wordWidth <= availableWidth) {
      curRowWidth += wordWidth;              // 整词计入本行
      nextElement = endElement;              // 判定边界推到词尾
    }
  }
  // 标点符号：跟着词一起算，不让句号孤零零顶到下一行行首
  curRowWidth += this.textParticle.measurePunctuationWidth(ctx, nextElement) * scale;
}

注意最后那行标点处理：句号、逗号不能出现在行首（避尾规则）。所以计算一个词能不能放进这行时，必须把它后面的标点也一起算进去——否则你会得到「词放得下了，但句号被挤到下一行开头」这种丑到没救的结果。中文还有另一半：行首不能是收尾标点（。，、；：？！）」），行尾不能是开口标点（（「）。标本项目把这张清单硬编码成一个二十来项的常量数组——不优雅，但每一项都是排出来的血泪。

坑四（最贵的那一个）：排版是 O(文档长度)，而每次按键都会触发

把上面所有东西合起来：一次完整排版 = 遍历全部字符 ×（查缓存量宽 + 折行判定 + 记录坐标）。两万字文档，就算缓存全命中，也要遍历两万个对象、累加两万次宽度、生成两万条坐标记录。这个成本无论缓存多好都降不到零，因为它和文档长度线性相关。

而用户打字时每次按键都触发「内容变更 → 重排 → 重绘」。大文档必然卡。业界的答案不是「把排版写得更快」，而是两招更粗的：只画可见页（第 3 章）、降级渲染（低端机关精细效果）。第 4 条 JD 里说的「性能优化」，在编辑器语境里首先是这两条架构决策，其次才是技巧。

把像素按批次交给 GPU

为什么一万个 fillText 会卡，而几十次不会——绘制层的合并、懒渲染与「画哪一页」的算计

坐标算好了，每个字都知道自己该待在哪。最直觉的画法是：遍历字符，一个一个 fillText。两万字文档 = 两万次 canvas 调用。这条路在台式机上能跑，在笔记本上会烧起来，在手机上直接躺平。

fillText 的真正成本不在渲染，在往返

一次 fillText 的开销分三块：① JS 到图形层的调用穿越；② 字形查找与整形（shaping）；③ 光栅化。后两项其实不慢——GPU 画字很快——真正慢的是第一项乘以次数：两万次调用，每次几百纳秒的边界穿越加起来就是几十毫秒，还没算驱动层的批处理被反复打断。

而同一行字里，绝大多数情况下相邻字符共享同一个字体串、同一个颜色。既然参数没变，为什么要分开画？标本项目的答案是：攒着，一起画。它有一个专门的 TextParticle（文本粒子）干这件事，核心是两个方法——record() 负责记账，complete() 负责结算：

文本合并绘制（真实源码，节选）TextParticle.ts · record / _render
public record(ctx, element, x, y) {
  // 样式变了才「收口」：把攒着的一起画掉，再开新一批
  if ((this.curStyle && element.style !== this.curStyle)
      || element.color !== this.curColor) {
    this.complete();
    this._setCurXY(x, y);
  }
  this.text += element.value;   // 只是拼字符串，还没画
  this.curStyle = element.style;
  this.curColor = element.color;
}

private _render() {
  if (!this.text) return;
  this.ctx.font      = this.curStyle;
  this.ctx.fillStyle = this.curColor;
  this.ctx.fillText(this.text, this.curX, this.curY); // 一次画一串
}

效果是数量级的：一篇普通文档里，样式变化点通常在几十到几百处，而不是几万处。于是两万次调用变成几十到几百次。有个细节值得划线：碰到图片、表格、控件这类非文本元素时，代码会立刻调一次 complete()——因为它们不走文本管线，不收口的话，后面那批字会「接」在错误的位置上。

为什么不能合并不连续的字？因为 fillText 的签名决定了：一次调用只能画一串从同一个起点开始、依次排下去的文字。它画不了「第 1 个字在 x=10、第 2 个字跳到 x=200」。所以合并只能发生在位置连续、样式相同的字符上——行内的每一次对齐调整、每一个上标、每一个行内空格缩进，都是一次强制收口。

合并绘制的核心不是「少画」，是把「参数相同」这个事实识别出来，让图形层一次处理完。

但合并解决不了「画多少」的问题

合并把「两万次 → 几十次」解决了，可它没解决另一件事：这两万字里，用户眼前只有两三页。三十页文档全部画一遍，画完的二十七页在屏幕外面安静地烧着 CPU。

所以第二招是「画哪一页」。标本项目的做法干净利落——给每个页 canvas 挂一个 IntersectionObserver，谁进视口就画谁：

private _lazyRender() {
  this._disconnectLazyRender();
  this.lazyRenderIntersectionObserver = new IntersectionObserver(entries => {
    entries.forEach(entry => {
      if (entry.isIntersecting) {
        const index = Number(entry.target.dataset.index);
        this._drawPage({ pageNo: index });   // 只画进视口的这页
      }
    });
  });
  this.pageList.forEach(el => this.lazyRenderIntersectionObserver.observe(el));
}

有意思的是源码里的一个条件分支：isLazy && isPagingMode——懒渲染只在分页模式下开启，连页模式（像网页那样连续滚动、没有「页」的概念）必须立即渲染。旁边留着一行注释：「连续页因为有高度的变化会导致canvas渲染空白，需立即渲染，否则会出现闪动」。性能优化从来不是免费的：懒渲染省下的 CPU，要用偶尔的空白闪动来还；连页模式的正确性，要用全量渲染来买。知道什么时候不该优化，比知道怎么优化更值钱。

DPR：一个数字决定清晰度，也决定显存

canvas 有一个反直觉的地方：内部像素尺寸和 CSS 显示尺寸是两回事。CSS 里写 width: 794px，但 canvas 的 width 属性如果是 794，在 2 倍屏上会被拉伸两倍显示——糊。正确做法是把内部尺寸放大 DPR 倍，再用 CSS 缩回去：

设备像素比（真实源码，节选）Draw.ts · setPageDevicePixel
const dpr = this.getPagePixelRatio();     // 默认即 window.devicePixelRatio
this.pageList.forEach((p, i) => {
  p.width  = width * dpr;     // 内部：真实像素
  p.height = height * dpr;
  p.style.width  = `${width}px`;   // 外部：CSS 尺寸
  p.style.height = `${height}px`;
  this._initPageContext(this.ctxList[i]);  // ← 尺寸变了，上下文被重置
});

这段代码里最容易漏的是最后那行。改 canvas 的 width/height 会把整个上下文状态清空——变换矩阵、字号、颜色、裁剪区，全部归零。所以每次改尺寸都必须重新初始化上下文。漏掉的症状极其诡异：改一次纸张大小，文字全部偏移、字号错乱、颜色变回黑。代码看起来完全正确，bug 却真实存在——因为「重置」发生在你看不见的地方。

还有一层：DPR 是会变的。把窗口从 1 倍屏拖到 2 倍屏，devicePixelRatio 就变了。标本项目专门监听了 matchMedia('(resolution: ${dpr}dppx)') 的变化事件来重设画布。这类「窗口跨屏拖动」是测试编辑器时最容易漏的场景——在公司 1 倍屏开发，用户在 3 倍屏上用，文字糊成一团。

显存账也要在这里算：A4 纸 794×1123 CSS 像素，DPR 2 下内部尺寸 1588×2246，RGBA 四字节，一页 14.3MB。一百页文档，光画布就 1.4GB——懒渲染只省绘制不省显存，这笔账第六章接着算。

光标与那一「下」

命中测试是坐标表的逆向解读：鼠标坐标怎么变回字符下标，以及光标为什么是一个 DOM 元素而不是画上去的

这一章讲的是整篇里最「反直觉」的两个东西。第一个：光标。第二个：点击。它们都是「从像素反推数据」的逆向工程——而逆向工程的质量，用户用一个词就能评价：手感。

光标：为什么不用 canvas 画，而用一个 div

第一反应肯定是「光标也画在 canvas 上」：在正确的位置画一条竖线不就完了。真做一遍就会发现三个无解的问题：

  • 它要闪。canvas 上做闪烁意味着每 500ms 重绘一次——而重绘的粒度是整个页面（第 3 章的结论）。为了一个光标的闪烁反复重画整篇文档，荒谬。
  • 它要跟着滚动走。canvas 的内容不随滚动重绘，画在里面的光标会跟文字错位。
  • 它要接输入法。中文 IME 需要一个真实的、可聚焦的 DOM 元素做组合输入（composition）和候选框定位。canvas 不能聚焦。

所以真实做法是三层分工：canvas 画字，一个绝对定位的 DOM div 画光标，一个隐藏的输入元素接键盘和 IME。标本项目里，光标就是 document.createElement('div') 造出来的一个普通元素，位置由坐标表算出：

光标的坐标计算（真实源码，节选）Cursor.ts · drawCursor

// 插入点：普通情况取「这个字的右边框」，行首插入点取左边界

三处细节值得盯住。第一：cursorLeft 取的是 rightTop[0]——光标画在「这个字的右边框」。因为光标表示插入点，插入点在第 n 个字之后，就是第 n 个字的右边；而行首没有「前一个字」，要用 leftTop[0]，这就是 hitLineStartIndex 分支的含义。第二：descent < 0 ? 0 : descent——某些字符的墨迹下界是负数，不兜住光标就会往上飘。第三：光标高度刻意比字框高一点（上下各加四分之一字高、封顶一个常数），纯视觉考量，但少了这点余量用户就会说「光标太局促」。

闪烁也不是 CSS 一挂了事。源码的逻辑是：每次光标移动，先保持实心（重置一个 500ms 的 setTimeout），500ms 内没有动静才加一个 CSS 动画类开始闪。因为输入中的光标必须实心——用户每敲一个键光标都闪一下会晃眼。CSS 动画只是「静止状态」的装饰，输入事件才是它的开关。

输入法为什么是编辑器的鬼门关。IME 组合期间，用户敲的是拼音，上屏的是汉字，中间还有候选框要跟着光标走。canvas 编辑器必须：① 让隐藏输入元素停在光标坐标上（否则候选框飘到屏幕左上角）；② composition 期间不重排（否则拼音字母被排进正文）；③ compositionend 时一次性插入整段汉字。三步任何一步错，中文用户第一分钟就会卸载你。

还有一层顺序问题：浮动图片（衬于文字下方/浮于文字上方）的命中要先于正文、或后于正文——必须和绘制顺序一致，否则「看见的顶层」和「点中的顶层」不是同一个东西。又一次：三个消费者必须对同一份数据达成一致。

命中测试是唯一一处「几何 → 数据」的逆向工程。它错一个边界条件，用户就会说这个编辑器「手感不对」——而且说不清哪不对。

撤销栈与自动保存的账

每一步一份全文档快照，和那个几乎没人愿意提的合并问题——两个机制长得像，代价完全不同

用户已经能看、能点、能打字了。接下来他会做两件人类必然做的事：按 Ctrl+Z；关掉页面再回来，期待内容还在。前者是撤销，后者是持久化。这两件事在实现上看起来是同一类问题——「记住过去」——但它们一个在内存里记账，一个在磁盘上记账，坑完全不一样。

撤销栈：一个闭包数组

标本项目的撤销栈，语法上简单到让人放松警惕：

HistoryManager（真实源码，节选）栈里存的是函数，不是数据
export class HistoryManager {
  private undoStack: Array<Function> = [];
  private redoStack: Array<Function> = [];

  public undo() {
    if (this.undoStack.length > 1) {
      const pop = this.undoStack.pop()!;
      this.redoStack.push(pop);
      if (this.undoStack.length) {
        this.undoStack[this.undoStack.length - 1](); // 执行「上一个状态」
      }
    }
  }

  public execute(fn: Function) {
    this.undoStack.push(fn);
    if (this.redoStack.length) this.redoStack = []; /* 新操作清空重做 */
    while (this.undoStack.length > this.maxRecordCount) {
      this.undoStack.shift();                 /* 超上限，丢最老的 */
    }
  }
}

栈里存的不是「逆操作」，而是「怎么回到那个状态」——一个闭包。入栈的瞬间，调用方把整份文档克隆一份，然后把「恢复这份克隆」包装成函数塞进栈里：

这套设计的三个后果，值得一条条摆出来：

  • 简单到不会错。没有「操作逆运算」，没有「相邻操作合并」的规则，撤销就是恢复一份快照。任何奇怪的编辑序列都能正确回退，因为根本不推理——只复制。
  • 内存与「文档大小 × 步数」成正比。两万字的文档，一份瘦身克隆约 2MB（每个字符一个对象），100 步 = 200MB。这是第 4 条 JD「内存占用高」里最隐蔽的一笔，因为它不发生在绘制层，性能面板的火焰图上它藏在堆内存快照里。
  • 撤销一次 = 全量重排重绘一次。恢复快照后调 render()，两万字文档按一次 Ctrl+Z 就是一次完整排版。撤销比打字还卡，就是这么来的。
快照式撤销的哲学：不推理历史，只复制过去。它用内存买正确性——对富文本来说，这笔买卖通常是划算的。

那个没人愿意提的合并问题

更难的问题在产品侧：用户连续敲 40 个键，每个键算一步吗？如果算，Ctrl+Z 一次只退一个字符，退完 40 个字要按 40 次——任何真实产品里都不可接受。浏览器原生输入框的行为是把一段连续输入合并成一次撤销。合并的判定条件，业内共识是四条：

  • 时间窗——两次编辑间隔小于 N 毫秒（常见 500ms～1s）就并成一步；
  • 语义窗——同类型操作才合并；插入图片必须单独成步；
  • 位置窗——光标移走了就断步，否则「改前面一段再改后面一段」会被并成一步，一次撤销毁掉两处编辑；
  • 断点——标点、空格、样式切换、输入法上屏，都是天然的「一步结束」。

值得诚实指出的是：标本项目的 HistoryManager 里一条合并规则都没有——每次 execute 无脑 push。也就是说，打 100 个字就耗尽 100 步上限，最早的 1 步已经被丢掉。合并的责任被推给了调用方（每个触发 render 的入口自己决定要不要提交历史）。这不是设计失误，是把「撤销粒度」当成了产品决策而不是技术参数：协作编辑器、写作工具、表单类应用对「一步」的定义完全不同。

一个面试级的问题：为什么不用 diff/patch 记撤销？因为富文本的「一个操作」在字符层面经常不是连续区间。一次「删除 + 粘贴」可能是「第 100–200 字符被替换」，语义上却是两个操作；基于 diff 的撤销会在复杂操作后产生「撤销了半个操作」的效果，用户立刻就能发现。快照法用内存换正确性，在这个场景下是清醒的选择。

自动保存：从「记住过去」到「保证不丢」

撤销栈在内存里，刷新就没了。持久化是另一套账。先交代一个也许让人意外的事实：标本项目（一个功能完备的 canvas 编辑器库）不做自动保存。我在源码里翻了三遍：localStorage 只出现在剪贴板兜底里——

库里的 localStorage 只干一件事（真实源码）utils/clipboard.ts

没有 IndexedDB，没有自动保存定时器，没有崩溃恢复，一处都没有。这不是遗漏，是边界划分：库不知道自己跑在什么环境里（本地单机？多用户协作？只读预览？），没资格替宿主做存储决策。它给出的是两样让你能自己做的东西：一个 contentChange 回调，和一份「取当前完整数据」的 API。JD 第 ⑤ 条考的其实是这条边界线两侧的知识都要有：库提供机制，宿主负责决策。

localStorage 能撑到哪一步

「每次内容变化就 localStorage.setItem」是最直觉的自动保存，也是最先炸的。三个硬限制：它是同步 API，写 2MB 字符串会阻塞主线程几十毫秒，而且正好发生在用户打字的时刻；配额只有 5MB 左右，两万字文档序列化后 1–3MB，图片一进来（base64 膨胀 33%）立刻超，超限时 setItem 同步抛异常，没接住就是白屏；它只有字符串，图片附件只能 base64，体积和 CPU 双输。

IndexedDB 的正确姿势

正解是 IndexedDB：异步、配额按磁盘比例给（通常几百 MB 起步）、能直接存 Blob（图片存二进制，不膨胀）。但它自带三个坑：写入是异步的，用户快速打字时多个保存任务并发，后发的可能先落地，必须用单调递增版本号或单写入队列；写入要节流合并，不能每次按键都写；要留两个版本，「自动保存草稿」和「上一次手动保存」各一份，否则一次误操作就把好内容覆盖了。

最小可用的自动保存骨架节流 + 关页兜底 + 版本号
let pending = null, timer = null, seq = 0;

function onContentChange() {
  pending = editor.getValue();            /* 拿一份快照（还不序列化） */
  if (timer) return;
  timer = setTimeout(flush, 1200);          /* 静默 1.2s 才写 */
}

async function flush() {
  timer = null;
  if (!pending) return;
  const payload = pending; pending = null;
  await db.put('draft', { seq: ++seq, data: payload, at: Date.now() });
}

/* 关页/切后台：最后一次机会。pagehide 比 beforeunload 可靠（移动端尤其） */
addEventListener('pagehide', () => { if (pending) flush(); });

状态恢复则在保存的对面：重启后要恢复的不只是内容——光标位置、选区、滚动位置、撤销栈要不要恢复，各是一个产品决策。最低配置是内容 + 文档版本号；版本号的作用是迁移：编辑器升级改了数据结构时，老草稿要先过一遍迁移函数再进内存，否则打开旧文档就是一次静默的数据损坏。

三笔烂账：多标签页、内存、媒体

JD 第 ④⑤⑥ 条的正面回答——三件事单独看都简单，放到同一份文档上就互相咬

到上一章为止，我们的编辑器还是「一个标签页里的孤岛」。真实用户不是这样的：他会开两个标签页对着改，会往文档里拖三十张照片，会把四万字的标书从头滚到尾。这三件事分别对应 JD 的第 ⑤④⑥ 条，而且它们互相咬：为省显存做的页 canvas 回收会伤媒体预览，为多标签做的同步会和自动保存打架，为媒体做的降采样又反过来救显存。

第一笔：多标签页，谁说了算

两个标签页打开同一份文档，各自内存里都有一份自己的副本。A 改了第三段，B 不知道；B 这时保存，A 的修改被覆盖。这就是「最后写入者胜出」——最常见的默认行为，也是最危险的，因为它静默丢数据：用户看不到任何报错，只是几天后发现那段话没了，而且无法证明是人的问题还是程序的问题。

解法有三档，成本完全不同：

方案机制防住什么防不住什么
互斥锁
最便宜		进编辑页先抢锁（Web Locks API 或 localStorage 心跳仲裁），抢不到进只读同时编辑——直接不让它发生假死的标签页占着锁不放（要做心跳超时）
乐观并发
推荐默认		每个标签页记住加载时的版本号，保存时带上 baseVersion；版本已变就弹「另一标签页已更新」静默覆盖——冲突时给人看，让人选用户选「用我的版本」时仍会覆盖（但至少是知情的）
实时协同
最贵		BroadcastChannel / storage 事件广播每次变更，OT 或 CRDT 合并几乎全部——那就是协作编辑产品了复杂度本身：CRDT 是独立领域，不是「加个库」

对多数单机产品，正确答案是第二档，再加一个关键细节：收到冲突不要自动合并，把对方的版本拉过来让用户看、让用户选。富文本的自动合并和撤销合并是同一类难题——「两处编辑」在字符层面可能并不冲突，在语义上却已经互相矛盾。另外，Web Locks API 值得单独一提，它是浏览器原生的互斥锁，十行代码就能防住双开：

第二笔：内存，页 canvas 是最大的不动产

第 3 章说过懒渲染：只画进视口的页。但有个细节当时按下没表——懒渲染省的是绘制，不省画布本身。每个页 canvas 在创建时就按「CSS 尺寸 × DPR」的内部尺寸申请了位图。算一笔账：A4 是 794×1123 CSS 像素，DPR 2 下内部 1588×2246，RGBA 四字节，一页 14.3MB；一百页文档，光画布就 1.4GB。懒渲染只保证「不画」，画布的位图仍躺在显存里。

所以认真的实现还要加一层：对远离视口的页，主动清零位图（canvas.width = canvas.height = 0），只留占位元素维持滚动条高度，滚回来时重画。没有现成 API 提醒你做这一层，只有内存曲线会提醒你。这也解释了第 3 章那个「连页模式必须立即渲染」的取舍的另一面：连页高度会变，位图回收的时机算不准，索性不省。

显存之外还有两块，都是第 5 章埋的种子：

  • 撤销栈——100 步 × 全文档快照，两万字 ≈ 200MB。上限应该随文档规模自适应：小文档 100 步，大文档降到 30 步。这是产品该做的自动降级，不是技术债。
  • 字宽缓存——键是「字符 + 字体串」，文档里出现过的组合全部留底。正常几十到几百 KB；但如果用户把表格里每个字都手动设成不同字号（真的会发生），缓存就膨胀。给缓存设一个上限（比如一万条，超了清最老的）是一行代码，但不能不写。

排查这类问题的顺序值得背下来：性能面板看火焰图（排版/绘制/脚本各占多少）→ 堆快照对比两次操作之间的增量（快照栈、缓存、监听器）→ Performance Monitor 看 GPU 内存。JD 第 ④ 条那句「能排查页面卡顿、内存占用高的问题」，考的就是这套流程的肌肉记忆。

第三笔：媒体文件，进编辑器之前的五道关

JD 第 ⑥ 条「图片、视频等媒体文件的前端处理」，在编辑器语境里的真实含义是：用户把一张 12MB 的手机原图拖进文档，编辑器不能卡死、显存不能爆炸、导出不能糊。这中间是五道关卡，每道都有标准答案：

关卡要防什么标准做法
① 读取同步 API 卡主线程File.arrayBuffer() / Blob 全异步，别用 FileReader 的同步思维
② 解码一张 4000×3000 的 JPEG 解码后占 48MB 内存，且解码同步createImageBitmap(blob)，可带 resizeWidth 让浏览器解码时顺手降采样
③ 方向手机竖拍的照片 EXIF 标了旋转，直接画会躺着createImageBitmap(blob, { imageOrientation: 'from-image' })——别自己解析 EXIF 字节，让浏览器做
④ 降采样显示宽度只有 554px 的图，存 4000px 是纯浪费缩到「显示宽 × DPR × 1.2 倍余量」再 convertToBlob({ type: 'image/webp', quality: 0.85 })
⑤ 存储base64 进 localStorage 膨胀 33% 且超配额图片以 Blob 存 IndexedDB，文档里只存引用 id，导出时再合并

第②③④步如果放主线程做，一张大图就是 200ms 的卡顿；用户一次拖十张，就是两秒白屏。所以这五道关的正确位置是 Worker：createImageBitmap、OffscreenCanvas.convertToBlob 在 Worker 里都可用，主线程只把 File 丢过去、把结果收回来。第 1 章那张账单里没有这一行，但它是「媒体文件的前端处理经验」的全部实务。

视频则要克制得多，准则一句话：永远不要把视频「放进」文档数据里。文档只存引用（文件 id + 时长 + 分辨率），预览帧用 <video> seek 到 0.1 秒抓一帧画上封面。视频动辄几百 MB，IndexedDB 写一次痛一次，而 <video> 元素自己会流式加载——把流式加载的东西复制进内存，等于亲手拆掉浏览器已经做好的优化。

媒体处理准则：文档存引用，不存内容；解码放 Worker，不占主线程；显示用多大，就存多大。

三笔账互相咬合的样子，值得再看一眼：媒体的降采样（第三笔）救了显存（第二笔）；多标签页的互斥锁（第一笔）让自动保存不必处理并发写入（第二笔的存储层）；撤销栈的自适应上限（第二笔）又取决于「当前是谁在编辑」（第一笔的锁状态）。JD 把这三条写成三行，是因为它们在实际工程里就是同一个礼拜里先后爆发的三个问题。

  • 第 3 天：光标与命中。隐藏 input 接输入，坐标表反查命中，行尾空白吸附。验收标准：点哪光标到哪；中文输入法整句上屏不乱跳。
  • 第 4 天：选区与撤销。拖选画高亮矩形；快照栈 + 500ms 合并窗 + 标点断步。验收标准：连打 40 字一次退光；插入图片单独成步。
  • 第 5 天：持久化与多标签。IndexedDB 节流保存 + pagehide 兜底 + Web Locks 防双开。验收标准：刷新后内容与光标都在；双标签第二个进只读。
  • 周末：挑最不顺手的那一点打磨。那一点就是你面试时最能讲的东西——因为卡住你的地方，也会卡住别人，而你已经走过来了。

一句诚实的提醒：这个最小实现不会比开源编辑器好，也不需要比。它的价值在于：做完之后，你去读任何一个真实编辑器的源码——本篇解剖的这个、或者任何别的——都能在 30 分钟内找到「断行在哪、命中在哪、撤销在哪」。JD 第 ③ 条筛的就是这个。

清单到这里。结语说三句想留下的话。

结语：接过来的是控制权，也是全部责任

写完这篇，回头再看那条 JD 的第 ③ 条，「只做过管理后台表格页面的不合适」就不再像门槛，更像一句忠告。表格页面的世界里，浏览器是权威：它排文字、画光标、管历史、存表单。可视化编辑器的世界里，你就是权威——每一个像素为什么在那、每一个字符为什么折到这、每一次撤销退到哪，都必须有人给出可解释的答案。浏览器交出来的不是自由，是六份责任。

这篇文章能给你的不是六份责任的全部细节，而是三个带得走的判断：

RULE 01 · 一份数据，三个消费者，一个都不能错

排版、绘制、命中测试读的是同一份坐标表。谁先算、谁缓存、谁失效，决定了光标和文字对不对得上。三个消费者的一致性，就是「手感」的技术实体。

RULE 02 · 每个白送的功能都要标价

光标要闪、输入法要候选框、撤销要合并、断行要避头尾——在 contenteditable 里这些是浏览器的事，换成 canvas 就全是你的事。动手前先把六笔账写下来；缺哪笔，上线后哪笔就变成事故。

RULE 03 · 库负责机制，宿主负责决策

canvas 编辑器库不自动保存、不做多标签仲裁，不是偷懒，是边界：它不知道自己跑在什么环境里。读懂库留给你的「内容变化回调 + 数据出口」，把存储决策接进自己的业务——这一层的判断力，比多会一个框架值钱。

这篇没解决的：协同编辑（OT/CRDT 是另一个世界，本篇的快照撤销在协同场景下完全不成立）；无障碍（canvas 对读屏软件天然失明，完整键盘导航 + ARIA live 补课的工程量常超过渲染本身，这是真实产品里最重的隐藏成本）；超大文档的极限优化（十万字级要分片排版 + Worker，本篇只点到为止）。
